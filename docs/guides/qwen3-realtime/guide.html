Making Qwen3-ASR realtime CONTINUOUS LIVE DECODING · EARS #144 · 2026-09-28

Qwen3-ASR-1.7B is an offline model: it transcribes a finished clip. This is how ears gets live, flicker-free text out of it on a stock vLLM server, with ~75 ms per update no matter how long you talk.

The problem

The live preview re-transcribed the whole clip every tick

Ghost text needs an update every 300 ms. With an offline model the obvious way is live_decoding = "repeat": send everything recorded so far, again, on every tick.

Every tick re-encodes and re-decodes audio that has not changed. Cost grows with the clip:

Measured, 33 s clip

p50 458 ms per tick, last tick 760 ms, 50.1 s of GPU time over 110 ticks. The 300 ms tick could not keep up.

The hack

Two facts about Qwen3-ASR made a cheap incremental decoder possible

1 · The encoder sees in 8 s windows

The audio encoder attends within fixed windows of n_window_infer = 800 mel frames at a 10 ms hop = 8 s. Windows never see each other.

So a finished window encodes to the same features forever. Send it as its own item, byte-identical every tick, and vLLM's caches serve it.

2 · The decoder is a chat LLM

The transcript is the assistant turn: language English<asr_text> then the text. An LLM can be handed the start of its own answer.

So force the text that has already settled as the assistant prefix; the model only decodes the new words.

Result: each tick re-encodes at most one 8 s window and decodes a handful of tokens. Tick cost stops growing with clip length.

Fact one in motion

Closed windows are encoded once; only the open window is redone

closed 8 s window: same base64 WAV every tick, cache hit open window: re-encoded each tick tail under 100 ms: left out
pcm.chunks(ENCODER_WINDOW = 8 * 16 000) · closed windows kept in self.closed · MIN_ITEM = SAMPLE_RATE / 10. Playback compressed 2x.

Fact one, the fine print

Many audio items, but one audio block

The prompt ears renders with its own chat template (33 s clip = 4 closed windows + a 1 s tail):

<|im_start|>system\n {prompt context} <|im_end|>\n<|im_start|>user\n <|audio_start|> pad · win 1 · 104 tok pad · win 2 · 104 tok pad · win 3 · 104 tok pad · win 4 · 104 tok pad · tail 1 s <|audio_end|> <|im_end|>\n<|im_start|>assistant\n language English<asr_text> Okay, so here is the plan for today. First, I want to … model continues here →

Why a custom template

The stock Qwen3-ASR template drops assistant turns and wraps every audio item in its own audio_start/end. Ours counts the items, emits one block of <|audio_pad|> placeholders, and appends the assistant prefix. With one item it renders exactly like stock.

Checked, not assumed

Teacher-forcing the same 109-token transcript, 8 s items in one block vs a single item: mean KL 0.0005, max 0.023, argmax 109/109. Separate markers per item: mean KL 0.0064, max 0.48. So: one block.

Fact two in motion

Settled text goes back in; only the last 3 words stay open

tick 0audio 0.0 sdecoded 0 words
language header (pinned) settled: forced as prefix, never re-decoded decoded this tick open: last 3 words, may be revised

Why leave words open

The newest audio often ends mid-word. At tick 4 the model hears "for to…"; one tick later it is "for today." Only the open words can change, so the fix costs nothing.

Why it is cheap

Speech is about 3 tokens a second. Each tick decodes only the new speech plus the reopened words, whether the clip is 3 s or 60 s long.

Text: the 2026-09-28 test clip. Tick contents illustrative; settling is computed live in this page with the same rule as settled_prefix(hypothesis, 3).

Fact two, the rules

How text settles, and what is refused

Settle = hypothesis minus last K words

stable = settled_prefix(hypothesis, 3), cut at a word boundary so the bytes are exactly what the model wrote. K is live_rollback_words.

Settled text only grows

A new stable is accepted only if it is longer and starts with the old one. A shorter continuation can never retract the forced prefix.

The final tick re-decodes the open words

On stop (last), nothing is held back. An empty continuation there is an error: it would silently drop the open words.

Runaway guard

max_tokens = 64 + 5 × seconds. A reply that ends with finish_reason: "length" is a loop, not a transcript, and is rejected.

Language pinning

A detected language X is pinned only after 2 s of audio and two decodes in a row agreeing; language None never counts. Forcing a wrong one turns the rest into a translation (English espeak once came out as Arabic, #153).

Graceful fallback

Not Qwen3-ASR, no /v1/models, or the server refuses a request template: ContinuousError::Unsupported, and ears goes back to repeat.

src/continuous.rs: step_inner, learn_language, settled_prefix, classify_error.

Long dictation

The context holds ~90 s of audio, so long recordings roll over

The server runs --max-model-len 2048. A segment ends at the first pause after 60 s, or at 80 s regardless. A pause is the last 300 ms under RMS 500 (about −36 dBFS). A fresh segment starts there; finished text stays in front, verbatim.

Measured, 147 s live recording

Rolled over twice, 364 ghost updates to the end, 331/331 words, 2.1% WER vs ground truth.

Going server side

The same decoder as a vLLM plugin: send only new audio

Plugin ears_stream serves WS /v1/ears/stream on the vLLM port. The client pushes new audio every 50 ms. The server starts a decode once 150 ms of new audio has arrived (min_step_ms), one decode at a time, same prompt, same windows, same settling.

Measured, 33 s clip streamed in real time

133 partials, decode p50 54 ms / p95 70 ms, final 54 ms after the audio ended, identical to full transcription. Three streams at once: ~60 ms each.

vllm-plugin/ears_vllm_stream: session._schedule, engine.VllmDecoder (TokensPrompt + multi_modal_data, 13 tok/s audio). Timing in the animation slowed 6x. Numbers: cloud PR #542 comment.

In one breath

Cache the past audio, force the past text, decode only the new

Audio

8 s windows = the encoder's own windows. Closed windows are byte-identical, so vLLM serves them from cache.

Text

Stability
